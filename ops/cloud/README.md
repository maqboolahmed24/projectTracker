# Cloud deployment

These manifests run the Azure starter deployment described in the [cloud evidence](../../docs/cloud-deployment-evidence.md) and [operating guide](../../docs/cloud-operations.md). Cloud checks cover HTTPS, restricted database TLS, synchronous replication, NFS permissions, encrypted backups, isolated replay and current-Owner workspace verification. The manifests do not provision resources or make another installation automatically verified. A PostgreSQL upgrade or image change requires renewed recovery checks. There is no automatic database failover.

Use a dedicated primary VM and an independent secondary VM. The primary runs the frontend, API, worker, application database, current security/control database and Caddy. The secondary runs the synchronous control standby and provides private NFSv4 exports on separate durable storage for the two encrypted backup repositories and checkpoint records. Configure NFS on the secondary host; it is deliberately not a privileged container in this stack. Both hosts need Docker Engine and a Compose version supporting required/raw `env_file` entries. The reviewed operator image includes its supported Node runtime, scripts and Docker client.

The fixed projects are `ukda-cloud-primary` and `ukda-cloud-standby`. Never combine these files with the local Compose files, override their project names, or run them on the workstation hosting local `ukda` data. API/worker/frontend/gateway have the `application` profile so a plain primary `up` only starts the databases. The full profile must be started only after the release gates below. Database container health alone does **not** establish synchronous durability.

## External configuration

Copy `cloud.env.example` outside the checkout and fill all settings. Keep passwords, private keys, identity setup and backup encryption configuration outside Git and outside the backup repositories. Private files must be mode `0600` in restricted directories. The public database CA file must be readable by the non-root Node user through its bind mount (mode `0644`); server certificates are also public material and may use `0644`. Compose file-backed secrets retain host permissions and are not a separate encrypted secret vault. Limit host and Docker-daemon access accordingly.

`UKDA_API_IMAGE`, `UKDA_FRONTEND_IMAGE`, `UKDA_RECOVERY_IMAGE`, `UKDA_CADDY_IMAGE` and the supervisor's required `UKDA_OPERATOR_IMAGE` must be immutable `repository@sha256:<64 lowercase hex digits>` references or full local `sha256:<64 lowercase hex digits>` image IDs reviewed for the target CPU architecture. API and worker share the same image. The recovery image must contain PostgreSQL 18, the reviewed pgBackRest version, and the current TLS/standby entrypoints in `ops/postgres`. Build `Dockerfile.operator` with `API_IMAGE` set to the reviewed application artifact; its build checks the copied Docker/Compose tools and compiled release imports. Local image IDs are not registry manifest digests: transfer a checked `docker save` archive, verify its checksum, run `docker load`, and verify the resulting exact image ID on each host. Alternatively explicitly pull a reviewed registry digest, including Caddy. No registry service is required for archive transfer. Every service uses `pull_policy: never`, so a missing image fails rather than silently pulling another artifact. There are no mutable-tag defaults or build steps in these manifests.

`UKDA_RUNTIME_ENV_FILE` is a private, externally prepared API env file. It contains:

- `DATABASE_URL`: limited `ukda_app_runtime` role at `app-db:5432/ukda_app`.
- `CONTROL_DATABASE_URL`: limited `ukda_control_runtime` role at `control-db:5432/ukda_control`.
- Both URLs require `sslmode=verify-full&sslrootcert=/run/secrets/database-ca.crt`; URL-encode passwords.
- Persistent `SECURITY_MASTER_KEY`, `SECURITY_KEY_ID`, `OPAQUE_SERVER_SETUP`, `OPAQUE_SETUP_ID`, and `AUTH_SERVER_IDENTITY` from the existing identity provisioning procedure.

`UKDA_WORKER_ENV_FILE` is a separate private env file containing only the two limited database URLs above. The worker does not receive the API's identity keys or OPAQUE setup. Use literal, unquoted values in these raw env files. Do not add either admin database URL. Separate host-only migration/operator configuration contains the admin credentials and stable `UKDA_OPERATOR_ID`; neither reaches the Node application containers. Set `UKDA_APP_ORIGIN` once to the permanent HTTPS origin. Existing signed local workspaces cannot be moved by changing their origin; initialize a fresh cloud workspace unless a reviewed migration exists.

The four database password files are required separately, with independent strong values. On first initialization, the cloud helper creates only limited runtime roles. Changing a mounted password later does not rotate an existing database role; use a coordinated credential rotation. Empty and known development passwords are rejected; never reuse local credentials. Do not run `docker compose config` without quiet mode against real files or publish resolved container environments.

TLS certificates must cover every name used by a verified client. For the suggested deployment that includes `app-db`, `control-db`, `127.0.0.1`, and the primary private address/hostname selected for replication. The entrypoint copies private keys to `/var/lib/postgresql/tls` before dropping privileges. This directory is outside `PGDATA`, so PostgreSQL physical backups do not contain those keys; preserve their external source files separately. The initialization helper rejects plaintext TCP authentication. Local privileged recovery uses Unix sockets inside the container. The standby mounts the same trusted CA at `/run/secrets/replication-ca.crt`; do not weaken `verify-full` to make a certificate mismatch pass.

## Private network and storage

- Public primary ingress: TCP 80/443 and optional UDP 443 for Caddy. Restrict SSH to the administrative source. Public standby ingress is unnecessary.
- Primary PostgreSQL replication binds only `UKDA_PRIMARY_PRIVATE_IP:5432`; allow it only from the standby `/32` address. Host operator ports bind `127.0.0.1:55432` (application), `127.0.0.1:55433` (control), and `127.0.0.1:3401` (worker recovery health).
- Secondary NFS TCP 2049 accepts only the primary private address. Keep this traffic inside the private network; NFS transport itself is not encrypted here. pgBackRest encrypts repository contents before writing them.
- Use explicit cloud firewall/NSG rules as well as the bind addresses. Docker-published ports need checking against the actual host firewall behavior. Container networks do not replace that boundary.

Set distinct `UKDA_APP_BACKUP_EXPORT` and `UKDA_CONTROL_BACKUP_EXPORT` NFSv4 paths on the independent secondary disk. Prepare both export roots with the PostgreSQL UID/GID of the pinned recovery image and mode `0700`; verify the image's actual IDs instead of assuming them. Root mapping must allow the entrypoint's `install -d -o postgres -g postgres /backrest`: one suitable restricted export maps squashed root to that PostgreSQL UID/GID using `root_squash,anonuid=<uid>,anongid=<gid>`, restricted to the primary `/32`, with synchronous server writes. Test ownership behavior on the selected NFS implementation before release. Avoid `soft` mounts and world-writable repositories.

The named Docker volumes remain mounted at `/backrest`, with no bind-mount replacement. `isolatedRestore` discovers the existing named repository volume and remounts it read-only in a `--network none` container; the Docker host performs the NFS mount. This preserves the existing recovery path while keeping stored backups off the primary VM. NFS outages may block a hard-mounted writer; never silently substitute a local directory or disable synchronous security commits.

`UKDA_RECOVERY_DIRECTORY` holds separate `app.conf`, `control.conf` and `replication.pgpass` files. Each pgBackRest config must use `/backrest`, the correct stanza, AES-256-CBC with its own generated encryption key, and the existing retention policy. Back up these secrets separately. The root operator requires its private configuration, including `app.conf`, to be root-owned `0600`.

Keep `UKDA_RECOVERY_RECORDS_DIRECTORY` on a third separately durable NFS export. Unlike the PostgreSQL repository exports, this export must preserve the operator's UID 0: restrict `no_root_squash` to the primary private `/32`, with root-owned `0700` export/mount directory and `0600` record files. Do not reuse the PostgreSQL root-squashing mapping; `RecoveryRecords` rejects mismatched owners. Repositories without these encrypted checkpoint sidecars are insufficient. The supervisor requires a real mount before starting, so a missing mount cannot silently redirect records to the primary root disk.

The supplied `maqbool-recovery.service` uses fixed host/container paths: `/opt/maqbool/release/ops/cloud`, `/opt/maqbool/secrets/cloud.env`, `/opt/maqbool/secrets/operator.env`, and `/opt/maqbool/recovery-records`. Set `UKDA_OPERATOR_IMAGE` to the loaded immutable operator image. The separate root-owned `operator.env` contains production mode, the permanent `APP_ORIGIN`, identity settings, a stable `UKDA_OPERATOR_ID`, and both limited and admin database URLs using `127.0.0.1:55432`/`55433`. All four URLs must verify TLS using the host CA path under `/opt/maqbool/secrets`; set `NODE_EXTRA_CA_CERTS` to that same CA. This operator configuration differs from API/worker's Docker-network URLs. The daemon gets host networking, the Docker socket, read-only release/configuration mounts and the writable checkpoint mount; Docker-daemon access is full host authority and must stay restricted to this maintenance identity.

## Release sequence and remaining proof

1. Verify account spending controls and approved resources independently; these files neither guarantee free service nor create resources. Prepare the two hosts, private routes, NSGs, persistent disks/NFS exports, permanent DNS, pinned images and external secret files.
2. Run `node ops/cloud/validate.mjs primary /absolute/cloud.env` on the primary and the equivalent `standby` check on the secondary. The primary check requires explicit external replication, TLS, the secondary private `/32`, this manifest's absolute path and a pinned operator image in the selected file; conflicting shell overrides are rejected. This reads resolved configuration in memory and reports only validation status. It does not contact PostgreSQL, start containers, validate certificate contents or confirm image availability.
3. Export the cloud operator settings into its environment: `UKDA_RECOVERY_COMPOSE_FILE` is this primary manifest's absolute path, `UKDA_RECOVERY_DIRECTORY`, `UKDA_RECOVERY_RECORDS_DIRECTORY`, `UKDA_RECOVERY_IMAGE`, `UKDA_RECOVERY_REPLICA_MODE=external`, `UKDA_REPLICATION_PRIMARY_HOST`, `UKDA_REPLICATION_ALLOWED_CIDR=<standby IPv4>/32`, and `UKDA_REPLICATION_REQUIRE_TLS=true`. The Compose interpolation variables also need to be present in that service environment. Passing `--env-file` to a separate Compose command does not export them to the operator.
4. Bootstrap fresh databases and prepare the replication role using the existing recovery setup procedure in external mode. This one-time setup writes/chmods the recovery secret directory, so use a controlled writable mount for bootstrap; the steady-state service mounts it read-only. Securely install `replication.pgpass` and the CA on the secondary, then start only `compose.standby.yaml` there. Setup waits for the matching standby, verifies its TLS/address, and persists `FIRST 1 (ukda_control_replica)` after it streams. Coordinate these steps on both hosts; a setup timeout leaves state for inspection, not automatic deletion.
5. Run privileged schema migrations and worker bootstrap once from the release environment. Verify `synchronous_commit=on`, the exact configured standby and live `sync_state=sync`. Stop the standby and prove a security write cannot commit; restore it and verify recovery. Never remove that setting to work around an outage.
6. Start the `application` profile with the primary manifest and external config. Supervise the separate host recovery operator (`recovery -- daemon`) with the same reviewed configuration. No Docker socket or admin database secret is mounted into API/worker/frontend. Confirm HTTPS, readiness, queues, `/health/recovery`, encrypted full backups and current checkpoint coverage.
7. Complete an isolated named-point restore and integrity check, then the owner activation, member invitation, new-device approval and recovery journeys through the permanent HTTPS origin. Confirm reload/restart behavior, certificate renewal, NFS outage handling and private port exposure. Record exact registry digests, reviewed source revision, certificate/backup custody and the rollback procedure before declaring the deployment usable.

Use explicit `docker compose --env-file /absolute/cloud.env -f /absolute/ops/cloud/compose.primary.yaml ...` commands for this stack. Do not use `down -v`, delete partial standby seeds, promote old control history, or restore over either current primary. Existing deployment and backup guidance in `docs/deployment.md` and `docs/backup-operations.md` still applies.

The Azure host layout, maintenance commands, credit boundary and certificate renewal procedure are documented in [cloud operations](../../docs/cloud-operations.md). Its evidence section distinguishes completed host checks from pending application and restore acceptance.
