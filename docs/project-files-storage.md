# Project file storage

Managed documents use a binary protocol separate from ordinary encrypted task envelopes. A signed manifest binds workspace, project, file identity, immutable version identity, source/output kind, upload operation, current device authority, key epoch, plaintext length and ciphertext chunk hashes. The filename, content hash, format, document reference, external path and random content key remain in client-encrypted metadata. The service never opens a local path or fetches an external reference.

Each binary chunk consists of a 24-byte XChaCha20 nonce, encrypted bytes and its 16-byte authentication tag. Associated data binds workspace, project, file identity, immutable version identity, key epoch and chunk index. SHA-256 covers the complete packed chunk. HTTP transports canonical base64url inside a bounded request; PostgreSQL stores the resulting bytes in `bytea`. A current approved device, exact origin, CSRF token, active provisioned project key scope and shared security fence protect every request. A changed security or key generation prevents an older staged upload from committing.

The first release accepts a managed file up to 25 MiB, with 256 KiB plaintext chunks and a 512 KiB HTTP request bound. Workspace admission counts ciphertext, nonce/tag overhead and encrypted metadata within 2 GiB; staged reservations and retained versions both count. Four managed uploads may be active in a workspace. The frontend further limits itself to two. FILE_STORAGE_LIMIT_BYTES supplies deployment-wide capacity, defaulting to 8 GiB and allowing a lower 2–8 GiB operational limit; serialize admission against that aggregate before allocation. This is a logical payload limit, not a promise that PostgreSQL pages, indexes, WAL and physical backups require only that amount of disk. Deployment measurements and free-space monitoring must set an appropriate lower limit before release.

`begin` reserves capacity and authenticates the immutable manifest. `chunk` accepts only a manifest-matching length and digest, and permits an identical chunk retry. `complete` rechecks current access, every retained chunk's bytes, the prior version and linked tasks before committing the ready version, latest pointer, quota transfer and operation receipt together. An identical operation retry returns its original receipt only under the same actor and data generation. Partially successful upload batches are independent per-file operations; there is no silent whole-batch rollback.

Staged uploads expire after two hours. Admission collects visible expired staged uploads; the privileged `collectExpiredFileUploads` operation collects expired uploads in projects whose access was removed. Collection releases binary reservations, retains the signed begin history's encrypted metadata quota, and cannot remove ready versions. The supervised recovery daemon collects up to 64 affected workspaces per tick, including idle or inaccessible workspaces. It uses the existing table-owner maintenance identity; application roles do not gain privileged cleanup access. Cancellation deletes staged bytes and retains its encrypted manifest and receipt. Current server routes do not provide deletion of ready evidence.

Ready versions and chunks are immutable at the database layer. Project file heads may advance and task links may select latest working content or an exact immutable version. Updating a shared file never changes old versions. Task links remain in the same project, and no more than 512 distinct document tasks may have file links. Files are paginated with a bounded 100-entry page; version reads identify exact immutable versions. External references have no managed chunks and count only their encrypted metadata toward cloud storage. Local verification is bounded to 2 GiB and must select bytes explicitly.

File submission and acceptance pin exact source/output versions, their manifest digests and the task and review-policy revisions. Independent review denies every assignee and every output author, including Owners. The frontend passes the displayed review context to the controller; a bounded checkpoint comparison rejects changed task, planning, security, links or signed evidence before generating byte proofs. Interrupted operations retain their signed ciphertext and exact flow identity; completed receipts remain available for explicit bulk retries and are cleared when the device is forgotten. A saved operation cannot be reused for another action, task, project or version.

`download_files` gates the product's download endpoint, while authorised previews use project read access. Previewing necessarily provides the viewing client with plaintext and cannot prevent screenshots or copying. Existing roles require an explicit signed capability change before gaining download authority; an active Owner has the reserved download ability.

Office previews run in a disposable local worker with a 15-second deadline and no document network access. DOCX, XLSX and PPTX archives are checked before parsing: matching local/central directories, safe unique paths, CRCs and bounded actual streaming inflation (16 MiB per entry, 80 MiB total) prevent dishonest compressed-size headers from bypassing the limits. Office preview input is bounded to 5 MiB, plain text/CSV to 2 MiB, spreadsheet previews to 10 sheets × 200 rows × 50 columns and presentation previews to 30 slides. RTF pictures are omitted. Rendered HTML/SVG is sanitised into a sandbox without scripts, links, forms, embedded resources or external requests; slide text is converted to inert SVG text instead of allowing foreign objects. PDF rendering uses canvas without scripting/annotation layers, at most 500 pages and 12 million pixels per displayed page. Image previews check encoded dimensions before decoding, at most 8192 pixels per side and 20 million pixels total. PDF/image loading and page rendering also stop after 15 seconds. Unsupported, unsafe, oversized and failed previews retain the original-file download/shared-drive fallback.

The additive permission catalogue retains the seven original built-in permissions. Signed custom definitions containing `download_files` use catalogue 2, and control/application constraint migrations admit that explicit snapshot. Changing a definition preserves an assigned snapshot; a signed access change applies the revised role. The focused acceptance verifies denied legacy downloads, permitted previews, explicit newly granted downloads, attenuation after access change, stale-session denial and reserved active-Owner downloads.

Because managed ciphertext and manifests live in the application database, encrypted full backups, WAL archives and point-in-time recovery include the same file commit. Version-2 recovery checkpoints enumerate immutable versions, actual chunk hashes and lengths, task links, evidence, deliveries and local service registrations. The original version-1 signed checkpoints retain their exact table catalogue. Recovery inventory limits metadata to 384 MiB, managed ciphertext to 2 GiB and rows/objects to 20,000; operational installation reads the paused owned database in 16-row pages without making an unbounded binary JSON file or host spool. Every ready chunk is checked before installation; the Owner additionally decrypts deterministic representative current/historical managed and external metadata samples before quarantine clears.

Restoration advances the existing data generation and preserves current security authority. It cancels staged uploads and unfinished deliveries, releases upload reservations, recalculates retained-byte quota, revokes active local services and clears disposable editor/publication/pairing grants. Old write receipts and permits cannot operate in the new generation. Ready historical versions and their signed evidence remain readable under current project access; preserved exact approvals may support a newly confirmed delivery, and an Owner may revoke those historical approvals. The dynamic application purge visits all tenant tables, including file versions, chunks, reservations and workspace storage usage. Ciphertext in expired backups follows the existing protected-backup retention policy; cloud recovery never contains external-drive bytes.

The real cross-component recovery acceptance additionally retains and decrypts a published delivery's destinations after the data generation advances, cancels an unfinished batch, revokes its local service, rejects old publication grants and replayed publication, and uses the retained exact approval for a fresh delivery. The focused fixture installs captured checkpoint rows; physical backup/WAL recovery remains separately tested by the recovery operator drill. Its execution is recorded in `test-results/project-files-delivery-restore.log`.

The explicit Owner workspace JSON export includes every ready version's verified plaintext metadata, hash, lineage, source/output kind and immutable manifest digest. It contains no content keys or encrypted envelopes. Signed planning transport is hydrated separately in 64-operation pages, bounded to 8192 operations/384 MiB, while individual pages and the graph remain 16 MiB and the final readable JSON remains 64 MiB. File manifests are exported in 100-version pages; a transaction-local database cursor bounds server capture memory and retains one statement snapshot. Any source or authority change blocks finalisation.

For file contents, the separate private archive download accepts up to 64 exact versions and 250 MiB of managed plaintext, uses current authorised downloads and a final unchanged-authority check, and returns a ZIP with a version manifest. External items contain only metadata and no fetched bytes. Archive creation never publishes to the official shared drive, and neither readable exports nor archives are stored as browser retry drafts. No document bytes enter a public object bucket, third-party converter or ordinary task envelope.

Development verification uses separate PostgreSQL 18 containers on ports 56432 and 56433, named `maqbool-files-test-app` and `maqbool-files-test-control`. Their synthetic credentials and test-only configuration remain in ignored `.local/testing/`; neither existing local data nor the live Azure database is used by these tests.

Real browser preview acceptance covers every supported Office/text format, PDF, PNG/JPEG/WebP, blocked active content and dishonest-size/unsupported/image-limit fallbacks in Chromium and WebKit (six passing cases retained in `test-results/project-files-preview-browser.json`). The installed Playwright Firefox engine fails before page launch with “Could not find profile folder”, including an explicitly created isolated profile, so these results do not claim Firefox preview acceptance. The existing branded Firefox/Safari compatibility reports cover their prior authentication workflows only.
